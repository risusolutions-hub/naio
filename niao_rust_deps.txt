==============================================================================
SECTION 2: SUGGESTED REWRITE ORDER (easiest -> hardest)
==============================================================================

TIER 1 - easy wins, pure algorithms:
  base64, uuid, dotenvy, rustls-pemfile, tar, indexmap, hmac(after sha2)
TIER 2 - medium, well-specified formats/protocols:
  serde_json, toml, bson, sha2, url, httparse, clap, chrono(+tz data),
  rand, rand_distr, tiny_http, tungstenite, lettre, suppaftp, redis,
  jsonwebtoken, tracing, ahash, dashmap, r2d2, http, num-bigint
TIER 3 - hard, large engineering projects:
  regex, serde(framework), flate2, zip, rayon, futures, tower/tower-http,
  axum, ureq, postgres, mongodb, sqlx, encoding_rs, matrixmultiply,
  tokenizers, fastembed
TIER 4 - very hard / reconsider rewriting:
  tokio        (an OS-level async runtime; consider building Niao's own
                event loop instead of porting tokio 1:1)
  hyper        (full HTTP/1.1 + HTTP/2 stack)
  rustls       (TLS crypto - hand-rolling crypto is a security risk;
                keep as native binding long-term)
  cranelift-*  (JIT backend for niao_vm - this IS your compiler backend;
                replacing means writing your own codegen)
  candle-*, llama-cpp-2/sys, ort
               (ML stacks binding to C/C++/GPU code - FFI is unavoidable;
                wrap them behind a Niao-native API instead)
TIER 0 - skip entirely:
  criterion (dev-only benchmark harness), thiserror/num-traits (Rust macro/
  trait glue with no Niao equivalent needed), hf-hub (already vendored)
